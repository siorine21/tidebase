# TIDEBASE 開発決定事項（DECISIONS）

> 実装中に下した技術判断のログ。仕様レベルの確定事項は
> `docs/handoff/TIDEBASE_確定仕様書_v2.4.md` を正とする。
> 判断基準（ハンドオフ 9.2 章）：コスト最小 > 無料枠内 > 確定仕様書に従う。

## 決定一覧

### D-001: 潮汐データソースは気象庁「潮位表」テキストデータ（2026-07-17）

- **決定**: 潮汐データ PoC のソースは気象庁の潮位表（推算値）テキスト
  `https://www.data.jma.go.jp/gmd/kaiyou/data/db/tide/suisan/txt/{year}/{station}.txt` を使用する。
- **理由**: 完全無料・API キー不要・国内観測点網羅。月額 $7 上限の制約下で
  有料 API（WorldTides 等）を避ける。年単位ファイルなので観測点×年でキャッシュすれば
  リクエスト数も最小。
- **備考**: 固定長フォーマット（毎時潮位 24×3 桁 + 年月日 + 地点記号 + 満潮4回 + 干潮4回）を
  `backend/app/services/tide.py` でパースする。開発サンドボックスからは外部ネットワーク
  ポリシーにより実データ取得が未検証（フォーマット仕様準拠 + フィクスチャでテスト済み）。
  実環境での疎通確認が Phase 1 の残タスク。

### D-002: 潮回り（大潮・中潮…）は月齢近似で判定（2026-07-17）

- **決定**: 潮回り判定は月齢（朔からの経過日数）を四捨五入した値のマッピングで行う。
  - 大潮: 0-2, 14-17, 29 / 中潮: 3-6, 12-13, 18-21, 27-28 / 小潮: 7-9, 22-24 /
    長潮: 10, 25 / 若潮: 11, 26
- **理由**: PoC として十分な精度で、外部依存ゼロ・計算コストゼロ。
- **備考**: 厳密には潮回りは朔望ベース。精度が問題になった場合に見直す。

### D-003: API 認証は Supabase JWT を FastAPI 依存で検証し、DB は RLS 前提でアクセス（2026-07-17 / 改訂 2026-07-17）

- **決定**: `Authorization: Bearer <Supabase JWT>` を PyJWT で検証（aud=authenticated）。
  - **第一**: JWKS エンドポイント（`{SUPABASE_URL}/auth/v1/.well-known/jwks.json`）
    経由で ES256 / RS256 を検証（Supabase の JWT 署名鍵移行後の標準）。
  - **フォールバック**: レガシープロジェクト向けに HS256 + `SUPABASE_JWT_SECRET`。
  - DB アクセスはリクエストごとに PostgREST クライアントを生成し、
    anon キー + ユーザー JWT で RLS を効かせる（共有クライアントのヘッダー
    書き換え方式は並行リクエストで認証が混線しうるため廃止）。
- **理由**: service_role キーの常用は RLS バイパスとなり事故リスクが高い
  （ハンドオフ 8.1 章「RLS を必ず有効化」）。Supabase 公式も共有シークレットでの
  検証を非推奨としており、新規プロジェクトのデフォルト署名は ES256。
  多層防御としてクエリ側でも `user_id = auth.uid()` 相当のフィルタを常に付ける。
- **備考**: supabase-py への依存を外し、postgrest + PyJWT[crypto] の直接利用に変更
  （Lambda パッケージも軽量化）。Supabase ダッシュボード → JWT Keys で
  プロジェクトの鍵タイプを確認すること。

### D-004: 釣果 API の部分更新は PATCH、更新時も作成時と同じ整合性検証を通す（2026-07-17）

- **決定**: `PATCH /api/v1/records/{id}` で部分更新。既存レコードとマージした結果を
  作成時と同じバリデーション（ボウズ時 `catch_count=0` 強制等）に通す。
- **理由**: 「ボウズなのに匹数 3」のような不整合をどの経路からも作らせないため。

### D-005: enum の内部値（2026-07-17）

- **決定**:
  - ヒットレンジ: `surface`（表層）/ `middle`（中層）/ `bottom`（底層）/ `bottom_direct`（ボトム直撃）
  - 水域区分: `saltwater` / `brackish` / `freshwater`（確定仕様書 14 章のとおり）
  - 公開範囲: `group`（デフォルト）/ `private`（確定仕様書 5 章のとおり）
  - 潮回り: `大潮` / `中潮` / `小潮` / `長潮` / `若潮`（表示値をそのまま API 値とする）

### D-006: スポット削除は釣果紐付き時 409 + 一括変更エンドポイント（2026-07-17）

- **決定**: `DELETE /api/v1/spots/{id}` は紐付く釣果が 1 件以上なら 409 を返し、
  レスポンスに件数を含める。`POST /api/v1/spots/{id}/reassign` で釣果の
  スポット一括変更（全件 or 指定 ID のみ）を行ってから削除する。
- **理由**: 確定仕様書 17 章のフロー（削除前に一括変更へ誘導）を API レベルで担保。

### D-007: DB スキーマ v1.2 差分は SQL ファイルで管理し Supabase SQL Editor で手動適用（2026-07-17）

- **決定**: ハンドオフ 2 章の追加・修正を `db/migrations/002_schema_v1.2_delta.sql` に集約。
  適用は Supabase SQL Editor で手動実行（v1.1 適用済み DB への差分）。
- **備考**: `group_members` の RLS は自己参照による無限再帰を避けるため
  SECURITY DEFINER 関数 `is_group_member()` を経由する。

### D-008: リポジトリ／ブランチ運用（2026-07-17）

- **決定**: 本セッションでは GitHub リポジトリ `siorine21/tidebase` の
  指定ブランチ `claude/phase-1-implementation-a97h2a` で開発する。
- **備考**: ハンドオフ 8.2 章は CodeCommit / `master` を前提としているが、
  実リポジトリの指示（GitHub）を優先。コミットメッセージは日本語・簡潔の規約を踏襲。

### D-009: 潮汐 API は認証不要の公開エンドポイント（2026-07-17）

- **決定**: `GET /api/v1/tide` はユーザーデータを含まない公的データのため認証不要とする。
- **備考**: 悪用（大量リクエスト）対策は API Gateway スロットリング（デフォルト）に委ねる。
  必要になれば認証必須に変更する。

### D-010: 当面はカスタムドメインなしで運用（2026-07-17）

- **決定**: `tidebase.app` ドメインと Route 53 ホストゾーンは当面使わず、
  CloudFront デフォルトドメイン（`dxxxx.cloudfront.net`）+ API Gateway
  デフォルト URL で運用する。ユーザー 1 人の想定で月額コストはほぼ $0 になる。
- **理由**: 固定費（ホストゾーン $0.50/月 + `.app` 更新 約 $14/年）が
  現構成の月額コストのほぼ全額を占めるため（コスト最小化の判断基準に従う）。
- **影響と備考**:
  - HTTPS は CloudFront デフォルト証明書でそのまま有効。ACM・Route 53 は不要。
  - Supabase Auth の Site URL / リダイレクト URL には CloudFront ドメインを設定する
    （将来ドメイン導入時に要更新）。
  - グループ招待 URL（Phase 4、確定仕様書 4.1 章の `https://tidebase.app/join?...`）は
    CloudFront ドメインベースに読み替える。トークンは 7 日で失効するため、
    将来のドメイン切替でリンクが無効化しても影響は軽微。
  - フロント配信と API は同一 CloudFront ディストリビューションに載せる
    （`/api/*` ビヘイビア → API Gateway オリジン）。単一オリジンになるため
    CORS 問題（レビュー指摘 8）自体が消える。Phase 2 のインフラ構成で採用する。
  - 後からドメインを導入する場合も、ACM 証明書 + CloudFront の代替ドメイン名 +
    DNS 追加のみで既存構成の作り直しは発生しない。
  - `tidebase.app` を既に取得済みの場合: ホストゾーンだけ削除すれば $0.50/月 は
    即座に節約できる。ドメイン自体は次回更新時に継続可否を判断すればよい。

### D-011: 日付境界はすべて JST 基準（2026-07-17）

- **決定**: 釣果の日付フィルタ（`date_from` / `date_to`）と「1日1釣行」の日付集計は
  `Asia/Tokyo`（+09:00）基準とする。naive な日時入力は JST とみなす。
- **理由**: `fished_at` は timestamptz（UTC 保存）のため、素の `DATE()` 比較だと
  JST 深夜 0〜9 時の釣行が前日扱いになり、潮汐相関の釣行回数がずれる。
- **備考**: v1.1 の `tide_correlation` ビューが `DATE(fished_at)` を使っている場合、
  `DATE(fished_at AT TIME ZONE 'Asia/Tokyo')` への修正が必要（v1.1 SQL 入手後に確認）。

### D-012: 釣果作成時に潮汐スナップショットをサーバー側で自動付与（2026-07-17）

- **決定**: `POST /api/v1/records` で `tide_snapshot` 未指定の場合、
  fished_at（JST 日付）から `{tide_type, moon_age, method: "moon_age_approx"}` を
  自動生成して保存する。クライアントが明示指定した場合はそちらを優先。
  `fished_at` の更新時、自動付与分（method で判別）は再計算する。
- **理由**: 潮汐相関分析（確定仕様書 13 章）の集計元となる潮回りデータを
  登録時点で確定保存するため（F-01 STEP5「潮汐・天気は自動取得して保存」）。
  月齢ベースなので観測点マッピング（未設計）に依存せず Phase 1 で成立する。
- **備考**: 将来、最寄り観測点の潮位（JMA）や天気（Open-Meteo 予定）を
  スナップショットに追加する際も `method` キーで世代を区別できる。

> 以下 D-013〜D-019 の詳細設計は `docs/design/TIDEBASE_設計補完_v1.0.md` を参照。

### D-013: 天気・波高データソースは Open-Meteo（2026-07-17）

- **決定**: OpenWeatherMap（確定仕様書 3 章）を Open-Meteo に置換。
  天気/風は Forecast API、波高は Marine API、過去釣行は Historical API。
- **理由**: OWM 無料プランに波高データが存在せず US-204 が実現不能。
  Open-Meteo は無料・API キー不要（キー管理も消える）。設計補完書 1〜2 章。

### D-014: スポット拡張フィールドの裁定（2026-07-17）

- **決定**: 確定仕様書 15.3（最小）と要件定義書 2.3（リッチ）の矛盾を裁定。
  Phase 1 で `spot_type` / `low_tide_only`（US-201 警告）/ `visibility` /
  `tide_station_code` を追加、残り（水深・底質・メモ類・対象魚種）は Phase 2。
  `spot_type` と `water_type` は独立。設計補完書 4 章。

### D-015: 出世魚判定は fish_name_rules マスタ + 提案 API（2026-07-17）

- **決定**: システムマスタ `fish_name_rules`（rule_group: buri/suzuki/sawara、関東呼称）
  と `GET /api/v1/fish-name/suggest` で実装。提案のみで強制しない。
  採用呼称は `fishing_records.fish_display_name` に保存し、`fish_species_id` は
  親魚種のまま（集計は親魚種・表示は呼称）。設計補完書 5 章。

### D-016: 写真は S3 署名付き URL 直アップロード方式（2026-07-17）

- **決定**: presign 発行 API → クライアント直 PUT → `photo_key` 保存 →
  取得時に署名付き GET URL を動的生成。バケット非公開・5MB 上限・
  キーは `photos/{user_id}/{uuid}`。設計補完書 6 章。

### D-017: 最寄り潮汐観測点は静的マスタ + 最近傍自動設定（2026-07-17）

- **決定**: 気象庁観測点マスタをリポジトリ内 JSON で保持し、スポット作成・
  座標更新時にハバーサイン距離で `tide_station_code` を自動設定（淡水は NULL）。
  潮汐 API は `spot_id` 指定も受け付ける。設計補完書 3 章。

### D-018: 釣行スコアの決定的アルゴリズム（2026-07-17）

- **決定**: 悪条件（嵐→雨/強風）から順に評価し、若潮・長潮はスコア 3 グループに
  含める。天気区分は Open-Meteo の WMO weather_code からマッピング。
  設計補完書 7 章。

### D-019: CI は GitHub Actions で pytest のみ、デプロイは当面手動（2026-07-17）

- **決定**: push/PR で pytest を実行するワークフローを追加。`sam deploy` の
  自動化（OIDC）は Phase 5 で検討。設計補完書 9 章。
- **備考**: API Gateway オーソライザーは採用しない（FastAPI 依存での JWT 検証に
  一本化。オーソライザー Lambda はコールドスタート二段化のデメリットのみ）。

### D-020: 構築・運用作業を Claude Code へ委任する体制（2026-07-17）

- **決定**: ユーザー作業を「一度きりの環境セットアップ（ネットワーク許可 +
  シークレット登録）と PR 承認」に最小化する。DB マイグレーション適用・
  スキーマ確認は Supabase Management API 経由のスクリプト
  （`scripts/supabase_admin.py`、適用済み管理テーブル `_migrations` で冪等）で
  Claude Code が実行する。手順は `docs/ops/委任運用ガイド_v1.0.md`。
- **理由**: SQL Editor での手動適用は作業負荷とヒューマンエラーの温床。
  Management API は HTTPS のみで完結し、サンドボックスのプロキシ経由でも動作する
  （Postgres 5432 直結はプロキシを通らないため不採用）。

### D-021: AWS 全面撤去 — GitHub + Supabase 完結構成へ移行（2026-07-17）

- **決定**: Lambda / API Gateway / S3 / CloudFront / SSM / EventBridge を廃止。
  - API: PostgREST 直接アクセス + DB トリガー/RPC（FastAPI 層は撤去、git 履歴に残存）
  - 潮汐のみ Edge Function（`supabase/functions/tide/`、気象庁プロキシ）
  - 写真: Supabase Storage / フロント: GitHub Pages or Cloudflare Pages（未決）
  - keepalive・CI: GitHub Actions（旧 EventBridge ping の置き換え含む）
- **理由**: シークレット最小化（AWS キーを渡す必要が消滅）・層削減・月額 $0 維持。
  詳細は `docs/design/TIDEBASE_アーキテクチャ移行_v1.0.md`。
- **備考**:
  - ドメインロジックは DB へ移植し、合成 v1.1 ベースライン上の SQL テストで検証
    （CI でも postgres サービスで毎回実行）
  - 月齢の丸めは四捨五入を正とする（D-002 どおり。旧 Python 実装は銀行丸めで
    .5 境界のみ相違、SQL/TS 実装で統一）
  - D-003 の JWT 検証層・D-016 の presign API・D-019 の pytest CI は本決定により失効
    （認証は supabase-js + RLS、写真は Storage SDK、CI は SQL/TS テストに置換）

### D-022: フロントは GitHub Pages・リポジトリは public 化（2026-07-18）

- **決定**: リポジトリを public にし、フロントは GitHub Pages（Actions デプロイ）で
  ホスティングする。
- **セキュリティ評価**（public 化の前提確認・2026-07-18 実施）:
  - 全コミット履歴をスキャンし、シークレット（AWS キー・JWT・PAT 等のパターン）の
    混入ゼロを確認済み
  - anon キーは将来フロントコードに含まれるが公開前提の値（防壁は RLS）
  - 釣果・スポット座標等の個人データは DB 側にありリポジトリに含まれない
  - セキュリティは「コードの秘匿」に依存しない設計（RLS・トリガーは公開されても安全）
- **運用**: public 化にあわせて GitHub の Secret scanning + Push protection を有効化し、
  以後の誤コミットを入口で遮断する。

### D-023: 実 v1.1 スキーマとの突合結果を正とする（2026-07-18）

- **背景**: 本番 DB を初めて直接確認した結果、想定台帳（設計補完書 8 章）と
  複数のカラムが食い違っていた。全テーブル 0 行だったため、既存カラムに
  合わせる方向で調整した（データ移行は不要）。
- **決定（実カラムを採用し、重複する追加は取りやめ）**:

  | 想定していた名前 | 実際に採用 | 備考 |
  |----------------|-----------|------|
  | `size_cm` | **`length_cm`** | 併せて `weight_g`（仕様 3 章の重量）も既存 |
  | `hit_range` | **`water_layer`** | ヒットレンジ |
  | `fish_display_name` | **`fish_name_local`** | 出世魚の採用呼称 |
  | `photo_key` | **`photo_url`** | Supabase Storage のパスを格納 |
  | `rod/reel/line/leader` | 既存のまま | v1.1 で既に存在 |

- **`fished_at` は DATE 型**（timestamptz ではない）。「1日1釣行」の単位と一致し、
  タイムゾーン境界問題が発生しないため DATE を維持する（**D-011 は釣果に関しては不要になった**）。
  時刻（朝マズメ等）の記録が必要になった場合は Phase 2 で `fished_time` を追加検討。
- **潮回りは `tide_type` カラムが正**。`tide_correlation` ビュー（確定仕様書 14.3 章の
  集計を実装済み）が参照しているため。`tide_snapshot`（JSONB）は月齢・算出方式などの
  詳細を保持し、トリガーが両者を整合させる。
- **追加したカラム**（v1.1 に不足していたもの）: `quantity_note`（仕様 1.3 章）・
  `visibility`（仕様 5 章）・`tide_snapshot` / `weather_snapshot`。
- **`methods_default` が 0 件だった**ため初期メソッド 10 件（仕様 8.3 章）を seed。
  既存の `handle_new_user` → `copy_default_methods` が機能するようになった。
- **テスト基盤**: `db/tests/baseline_v1.1_synthetic.sql`（想定ベース）を
  `baseline_v1.1_actual.sql`（実スキーマ）に置き換え、以後は実態に対して検証する。

### D-027: フォント同梱と線画アイコン統一（2026-07-29）

- **決定**:
  - Google Fonts の読み込みを廃止し、Bebas Neue（見出し）と JetBrains Mono（数値）の
    latin サブセットを `frontend/vendor/fonts/` に同梱する（計 76KB）。
    **日本語は端末標準フォント**（Hiragino / Noto Sans JP / Yu Gothic 等）を使う。
  - UI の絵文字を全廃し、**Lucide（ISC License）の線画アイコン**に統一する。
    使用アイコンのみを `frontend/assets/icons.js` にインライン SVG として展開し、
    色は `currentColor` でテーマに追従させる。
- **理由**:
  - フォント: アプリを開くたびに Google へ IP が送られる状態を解消する。
    日本語フォントは端末標準で十分な品質があり、数 MB の配信も不要になる。
  - アイコン: 絵文字は OS ごとに描画が変わり、カラフルでカラシ×ネイビーの
    デザインと調和しないため。線画アイコンはサイズ・色・線幅を統一できる。
- **備考**: 外部への通信は Supabase・Open-Meteo・国土地理院タイルのみになった
  （実ブラウザで通信先を検証済み）。

### D-028: 魚種マスタは水域区分ごとに sort_order で並べ、クロダイを汽水へ移す（2026-07-29）

- **背景**: 魚種を 7 種追加（アジ・メバル・カサゴ・カマス・キス・イカ・タコ）した結果、

### D-031: ユーザー ID はローカルのセッションから取り、座標は日本国内に限る（2026-07-30）

2 件の不具合の原因と対処。どちらも「外部要因で null / 不正値になったものを
そのまま送っていた」という同じ構図だった。

- **不具合 1: 日の出・日没の時刻が実際と違う**
  - **原因**: スポットの座標が `(0, 0)` のまま保存されていた。旧の釣果入力
    フォームは緯度・経度を数値入力させており、空欄だと `Number("") === 0` が
    `Number.isFinite()` を通ってしまうため。(0, 0) は大西洋ギニア湾なので
    Open-Meteo は**日の出 15:02 / 日没 03:09（JST）** を返していた。
  - **対処**:
    - `isCoordinateInJapan()`（緯度 20〜46 / 経度 122〜154）を追加し、
      天気・日の出日没に使う前に必ず通す。使えない座標なら潮汐地点の座標で代用する。
    - Open-Meteo の `daily.sunrise/sunset` が対象日と違う日付を返したら採用しない
      （座標とタイムゾーンが噛み合っていないサイン）。
    - `spots` に CHECK 制約 `spots_coordinates_in_japan` を追加（**NOT VALID**：
      既存の不正行は残したまま、新規の書き込みだけを検証する）。
    - 位置未設定のスポットは、ホームで警告＋直し方を案内し、スポットマップの
      ピンから外し（(0,0) を含めると地図が世界全体まで引くため）、
      スポット詳細では地図を静岡県の初期表示にしてタップで設定できるようにした。
- **不具合 2: ルアーメーカーを作成すると「権限がありません」**
  - **原因**: `currentUserId()` が `auth.getUser()` を使っており、これは毎回
    `/auth/v1/user` を叩く。レート制限や通信エラーで失敗すると null を返し、
    `user_id: null` で INSERT していた。PostgREST は NOT NULL 違反より先に
    RLS を評価するため **「new row violates row-level security policy」= 42501**
    になり、画面には「権限がありません」と出て原因が分からなくなっていた。
    （`getUser` を 429 に固定して再現・修正を確認した）
  - **対処**:
    - `currentUserId()` を `auth.getSession()` に変更。ローカルのセッションから
      取るのでネットワークに出ない（期限切れなら supabase-js が自動更新する）。
    - 書き込み前用に `requireUserId()` を追加し、ID が取れないときは RLS 違反に
      させず「セッションが切れました。再度ログインしてください。」を出す。
      スポット・釣果・メーカー・タグ・レシピの全 INSERT をこれに寄せた。
    - あわせて `toJapaneseError()` に一意制約違反（同名のメーカー／タグ／魚種）と
      座標 CHECK 違反の日本語訳を追加した。
- **教訓**: 書き込みに使う値が外部由来（ネットワーク・フォーム入力）なら、
  送る前に検証する。RLS 違反メッセージは「権限」ではなく
  「値が想定外」の可能性もある。

### D-033: keepalive の ping 先を実テーブルに変更（2026-08-05）

### D-035: SCR-003 は「カレンダー → サマリ → グラフ」の順にし、グラフは横スクロールで日送り（2026-08-05）

- **並び順**: 週間カレンダーを最下部から**サマリの上**へ移した。

  カレンダーの選択に反映される。カレンダーの日を押すとその日までスクロールする
  （どちらから操作しても状態が 1 つに収束する）。

### D-038: 潮位グラフは単調 3 次補間で滑らかに描く（2026-08-07）

- **背景**: 毎時の点を直線でつないでいたため、カクカクして見えていた。
- **決定**: **単調 3 次補間（Fritsch–Carlson）** で 3 次ベジェのパスを作る。
  - Catmull-Rom などの一般的なスプラインは山谷で行き過ぎ（オーバーシュート）が
    起き、干潮の谷が軸を突き抜けて描かれることがある。単調性を保つ方式なら
    補間値が元データの範囲を出ないので、その心配がない。
  - 実データで検証: 隣り合う線分の最大折れ角が **47.7° → 2.6°**、
    補間後も値域は元データと同じ（29〜137）。
- **満潮・干潮の実測値も曲線に含める**: 気象庁の満干潮位は毎時値の最大／最小を
  超えることがある（例: 毎時 115cm に対し満潮 116cm）。毎時値だけで描くと
  満干の点が曲線から浮くため、実測の (時刻, 潮位) も補間の点列に入れる。
  これで曲線が実際の満干を通り、点と曲線が一致する。
- **テスト**: `frontend/tests/smooth_path.test.mjs` を追加し、`make test-frontend`
  と CI で実行する（3 次ベジェを実際に評価して、オーバーシュートしないこと・
  元の点を通ること・折れ角が小さくなることを確認する）。
  `app.js` はブラウザ前提で import できないため、対象関数をソースから切り出して評価している。

### D-039: 釣果は編集でき、ウィザードは入力を覚えている（2026-08-07）

- **匹数の検証**: ボウズは `catch_count = 0` で保存されるので、解除すると 0 のまま
  更新して DB トリガーの例外（`catch_count は 1 以上が必要です`）を踏む。
  読み込み時に 1 に戻し、送信前にも 1 以上かを画面側で確かめて STEP1 へ案内する。
- **検証**: Playwright で本番 Supabase に対して 14 項目（新規登録・離脱と復元・破棄・
  編集の読み込みと保存・ボウズ化と解除の双方向）を通し、全画面で JS エラーが
  出ないことも確認した。テストデータは削除済み。

### D-041: 会員登録は招待リンク限定。共有は「列を絞ったビュー」で行う（2026-08-07）

- **要望**: 友人 3 人を招待したい。不特定多数には公開しない（LINE などで招待した
  人だけ登録できる）。他人の釣果だと分かるようにし、他人の釣果は編集できないようにする。

**① 招待した人だけが登録できる**

- Supabase Auth の一般公開サインアップは **無効のまま**（`disable_signup = true`）。
  これが一番外側の壁で、動かさない。
- 登録経路は Edge Function `invite`（`verify_jwt = false`）ひとつだけ。
  `group_invites.token`（UUID v4）を持っている人だけが、service_role の
  Admin API 経由でアカウントを作れる。**トークンの所持が認可**になる。
- 招待は **1 回きり・7 日間有効・人数上限 8 人**。取り消しもできる。
- **アカウント作成の前に招待を確保する**（`claim_invite` の単一 UPDATE）。
  同じリンクを 2 人が同時に開いても 1 人しか通らない。作成に失敗したら
  `release_invite` で戻す。逆順（作ってから確保）だと、招待が無効だったときに
  グループに入れないアカウントが残ってしまう。
- **確認メールは使わない**（`email_confirm: true` で作る）。Supabase の内蔵メールは
  1 時間 2 通の制限があり、届かないと招待した人が対処できない（D-034 と同じ判断）。
- `peek_invite` / `claim_invite` / `release_invite` / `redeem_invite` は
  **service_role にだけ EXECUTE 権限**を与える。ブラウザ（anon / authenticated）からは
  `permission denied` になることを実機で確認済み。

**② 他人の釣果の見え方 — 既存の RLS は 1 つも緩めない**

- `fishing_records` / `spots` / `lure_recipes` / `profiles` の RLS は
  **「自分の行だけ」のまま**にした。共有は読み取り専用ビュー
  `public.record_feed` を新設して行う（`security_invoker = false` を明示）。
- なぜビューか:
  - **他人の釣果を編集できないことが、画面の作りではなく DB の性質になる。**
    書き込みは今まで通り `fishing_records` に対して行い、他人の行は RLS が拒否する。
    URL を直接叩いても、API を直接叩いても変わらない（実機で確認）。
  - **列を選べる。** ビューにスポットの緯度経度を入れていないので、
    共有されるのは「スポット名と水域区分」まで。釣り場の座標は API 経由でも出ない。
    「どこで釣れたか」は名前で伝わり、正確な座標は渡さない、という線引き。
  - RLS を広げる方式だと、`spots` を読めるようにした時点で座標も一緒に出てしまう。
- 出す行は「自分の全件 + 同じグループの人の `visibility = 'group'` の釣果」。
  見せたくない釣果は今まで通り「自分のみ」にすればグループにも出ない。
- ビューは RLS を迂回して動くので **WHERE 句そのものが認可**。
  db/tests に「他人の非公開が出ない」「グループ外の人の釣果が出ない」
  「未ログインでは 0 件」「座標の列が存在しない」を明示的に入れた。

**③ 画面**

- 一覧・ホーム・スポット詳細では、他人の釣果に**投稿者名のチップ**を付け、
  左に青い線を入れる。自分の釣果には何も付けない（普段の見た目を変えない）。
- 釣果詳細は他人のものだと「◯◯ さんの釣果です（閲覧のみ）」を出し、
  **編集・削除ボタンを出さない**。公開範囲の行も出さない（自分にしか意味がない設定のため）。
- 一覧に「投稿者」の絞り込み（自分 / グループ全員 / メンバー）を足した。
  ただし**グループの釣果が 1 件も無いうちは表示しない**（1 人で使っている間は不要）。
- 招待リンクは設定 → GROUP から発行し、コピーして LINE で送る。
- ニックネームは登録時に必須にした。共有したときに「メンバー」ばかりでは区別できない。

**④ その他**

- `group_invites.used_by` の外部キーが既定（NO ACTION）だったため、
  招待で入った人が退会しようとすると外部キー違反で消せなかった。
  `ON DELETE SET NULL` に直した（005 と同じ種類の落とし穴）。
- `scripts/deploy_function.py` を追加。Edge Function も Management API 経由で
  デプロイでき、ダッシュボードでの手作業が要らない（委任運用ガイド 1 章）。

**検証**: DB テスト（招待の確保・二重使用・期限切れ・共有範囲・人数上限・退会）に加え、
Playwright で実際に 2 アカウントを使い 22 項目。招待リンクからの登録、招待なし・無効・
使用済みの拒否、共有の見え方、他人の釣果を URL と API から書き換えられないことまで確認した。

### D-043: 招待を作れるのは管理者だけにする（2026-08-07）

- **要望**: 招待は管理者（本人）だけが使える機能にしたい。招待して入ってきた人が、
  さらに別の人を招待できるようにはしたくない。
- **見つかった穴**: D-041 では画面側でオーナーにだけ招待 UI を出していたが、
  **DB の権限としては塞げていなかった**。実際に 2 経路が空いていた。
  1. `group_invites` の `"creator manage"` ポリシーが
     `WITH CHECK (created_by = auth.uid())` だけで、メンバーが自分を
     `created_by` にして招待を作れた。
  2. `groups` の `"create own"` が誰でも通るため、メンバーが**自分のグループを
     新規作成**して、そのオーナーとして招待し放題にできた。
  - どちらも「アカウントを作れる」ことが本質的な被害（無料枠の消費・
     知らないユーザーの増加）。データが見えるわけではないが、要望の趣旨に反する。
- **決定**: 管理者の台帳 `public.app_admins` を作り、
  **グループ作成と招待発行を管理者に限定**する。
  - `app_admins` は **RLS 有効・ポリシーを 1 つも作らない**。
    PostgREST からは誰も読み書きできず、管理者の追加は DB 直（Management API）のみ。
    「アプリの操作では絶対に増えない」ことが要件そのものなので、画面から触る経路を作らない。
  - RLS: `groups: create own` に `is_app_admin()` を追加。
    `group_invites` は `"admin manage"` 1 本にまとめ、
    **管理者 かつ そのグループのオーナー かつ `created_by = auth.uid()`** を要求する。
  - **トリガーでも二重に担保**（`guard_invite_creator`）。`auth.uid()` ではなく
    行の `created_by` を見るので、RLS を迂回する service_role や管理用 SQL から
    入れた行にも同じ規則が効く。
  - 移行: 既存グループのオーナー、無ければ最初に登録したユーザーを管理者として投入。
    本番では本人 1 人が入った。
- **画面**: 管理者でない人には招待 UI もグループ作成 UI も出さない。
  グループ未参加の非管理者には「管理者から招待リンクを送ってもらってください」と出す。
  判定には RPC `is_app_admin()` を使う（**表示の出し分け用**で、制限の実体は RLS）。
- **テストの作り**: RLS は所有者権限の `DO` ブロックでは効かないため、
  `SET ROLE authenticated` + `request.jwt.claim.sub` を設定して、アプリと同じ経路で
  「メンバーは招待を作れない／グループを作れない／管理者台帳を読めない」を確認する。
  加えて**対照実験**（同じ authenticated ロールでも管理者なら通る）を入れた。
  これが無いと GRANT 漏れなどの別要因による失敗を「拒否できている」と読み違える。
- **実機確認**: 招待された人のブラウザから API を直接叩き、招待の作成・`created_by` の
  偽装・自分のグループ作成・管理者台帳の読み取りがすべて `42501` で拒否されることを確認。
  管理者側は今まで通り発行できる。

- **決定**: `fishing_records.fished_time TIME`（NULL 可）を追加する。
  - **タイムゾーンを持たない `TIME`** にする。`fished_at` と組で
    「JST の壁掛け時計の時刻」として読む。アプリ全体が JST 固定（D-011）なので、
    ここで tz を持つと日付との整合がむしろ取りづらくなる。
  - **NULL 可**にする。既存の記録には時刻が無く、後から思い出せないものを
    埋めさせたくない。「行ったが時間は覚えていない」を記録できなくすると、
    記録そのものを諦められてしまう。
- **既定値は空にした**。「今」ボタンでワンタップ入力できるようにしてある。
  釣行日と同じく現在時刻を自動で入れる案もあったが、家に帰ってから入力したときに
  **間違った時刻が黙って入る**ほうが困る。潮位を引くための値なので正しさを優先した。
- **潮位は保存せず、表示のたびに計算する。**
  - 気象庁の潮位は推算値なので、時刻さえ残っていれば後からいくらでも引き直せる。
    保存すると、あとで潮汐地点の設定（時差・潮高比）を直したときに
    古い値が残ってしまう。
  - スポットに紐付いた潮汐地点をそのまま使うので、浜名湖の細分地点なら
    基準観測点からの推算（D-030）が効く。実測で確認: 弁天島の 05:30 は
    毎時値 51cm（05:00）と 39cm（06:00）の中点 45cm と一致。
- **出す情報**: 潮位（cm）・潮の動き（上げ潮 / 下げ潮 / 潮止まり前後）・潮汐地点に加え、
  **その日の潮位グラフに釣れた時刻の印**を出す。数値だけより、満干のどのあたりで
  釣れたのかが一目で分かる。印は緑（現在時刻のカラシと区別するため）。
  - 潮の動きは前後 30 分の差で判定する。毎時値の線形補間なので、
    これより細かくしても精度は上がらない。
- **共有された釣果でも潮位を出せるようにした**。`record_feed` に
  `spot_tide_station_code` / `spot_tide_area_code` を追加する。
  基準観測点と時差が分からないと推算できないため。
- **一覧・ホーム・スポット詳細**では日付の後ろに時刻を出す（未入力なら日付だけ）。

### D-045: 釣果写真は「原本を持たず、表示用コピーだけ」保存する（2026-08-07）

- **背景**: 無料枠のストレージは 1GB。原寸（3〜5MB）で上げると 4 人で 1 年もたない。
- **決定**: **原本は保存しない。** ブラウザ側で縮小してから上げる。
  - 表示用: 長辺 1600px / WebP（品質 0.82）
  - 一覧用サムネイル: 長辺 400px / WebP（品質 0.75）
  - **実測**（4032×3024・2.3MB の写真）: **258KB + 10KB = 268KB。8.8 分の 1。**
    1GB で約 3,900 枚 = 4 人が年 80 枚上げても 10 年以上もつ。
- **これは妥協ではない**という整理: 原本はスマホのカメラロールにある。
  アプリは釣行ログに添える表示用コピーを持てばよく、写真の保管庫ではない。
  そう捉えると「容量のために画質を落とす」のではなく、最初から表示用を作るのが正しい。
- **バケットは非公開**にする。招待制でここまで作った共有（D-041 / D-043）に対し、
  URL を知っていれば誰でも見られる公開バケットは明らかな弱点になる。
  表示は署名付き URL 経由で、**発行時に RLS が効く**のが認可の実体。
- **台帳 `record_photos` を別に持つ**。Storage だけだと「どの釣果の何枚目か」
  「並び順」が持てず、釣果を消したときに何を消せばよいかも分からない。
  署名付き URL の可否も、台帳に載っているパスかどうかで判断する
  （台帳に無いパスは誰にも見えない）。
- **ポリシーから釣果を参照するときは SECURITY DEFINER 必須**。
  素の副問い合わせで `fishing_records` を引くと、そちらの RLS（自分の行だけ）が
  効いてしまい、共有された釣果の写真が常に 0 件になる。
  `record_visible_to_me()` を通す（テストで実際に踏んで気づいた）。
- **削除の順番**: 釣果を消すと台帳は CASCADE で消えるが、Storage の実体は残る。
  **先に実体を消してから記録を消す。** 逆順だと、消すべきパスが分からなくなる。
  台帳に載せられなかった実体も、その場で消す（誰からも辿れないゴミになるため）。
- **写真は「保存したときにまとめて反映」**する。新規登録では釣果 ID が
  まだ無く、どのみち保存後にしか上げられない。編集も同じ扱いにして経路を 1 本にした。
- **EXIF は canvas を通した時点で落ちる** — 位置情報が写真から漏れない。
  向きは `imageOrientation: "from-image"` で補正する（指定しないと横倒しになる端末がある）。
- **副次的に直したこと**: 編集画面で写真の読み込みを待ってからステップを決めていたため、
  ボウズの編集で STEP1 が一瞬見えてから STEP3 へ飛んでいた。ステップの決定を先に出した。
  また、読み込み中にステップを触られたらそちらを優先する（`userMovedStep`）。
- **実機で分かったこと（2026-08-08 追記）**: iPhone からのアップロードは通り、
  1600×1200 まで縮小されたが、**形式が JPEG になった**（iOS Safari は canvas から
  WebP を書き出せず、フォールバックが働いた）。同じ 1600px で
  **WebP 484KB に対し JPEG 756KB** と 1.5 倍。
  → **品質固定をやめ、容量を目標にする**方式に変更した。
    品質 0.82 → 0.7 → 0.6 → 0.5 と順に試し、表示用 420KB / サムネイル 40KB に
    収まった時点で止める。端末が使える形式に関係なく容量が読める。
    実測（WebP 258KB / JPEG 315KB）で、どちらも予算内に収まることを確認済み。
- **検証**: DB テスト（非公開バケット・共有範囲・台帳に無いパス・CASCADE）に加え、
  Playwright で実画像を使った 18 項目（縮小の実測・アップロード・署名付き URL での表示・
  一覧サムネイル・編集での追加と削除・釣果削除時に実体まで消えること）。

### D-046: 週間カレンダーは「見出しで週を示し、ボタンは操作に徹する」（2026-08-08）

- **報告**: 矢印で週を切り替えても「今週」の文字が変わらない。
- **原因**: 中央の「今週」は*操作*（今週へ戻る）だが、左右の矢印に挟まれているため
  *見出し*（いま見ている週）に見えていた。実際には見出しは別にあり、
  日付の範囲（08/02 — 08/08）だけが変わっていた。
- **決定**: 役割を分ける。
  - **見出し**に相対的な週名を足す: 「今週 · 08/02 — 08/08」「来週 · …」「2 週間前 · …」。
    矢印で送ると、ここが必ず変わる。
  - **「今週」ボタンは操作のまま**。ただし**今週を見ているときは押せなくする**。
    押しても何も起きないボタンが常時光っていると、見出しと誤解される。
- 数字（日付の範囲）だけでは「今からどれくらい先か」が読み取りにくい。
  釣行の計画は「来週の土曜」のように相対で考えるので、言葉を添えるほうが速い。
- **2026-08-08 追記（これでも足りなかった）**: 見出しに週名を出し、今週にいるときは
  ボタンを押せなくしても、**来週を見ている画面に「今週」と書いてあること自体**が
  違和感として残った。無効化しただけでは文字は消えない。
  - **左右の矢印に挟まれた真ん中は、どうしても「いま見ている週」の表示として読まれる。**
    ここに操作の名前を置く限り、状態と食い違う瞬間が必ず出る。
  - **決定**: 真ん中は `<span>` にして**表示に徹する**（今週 / 来週 / 2 週間後 …）。
    今週へ戻す操作は、**今週から離れているときだけ**カレンダーの下に出す。
    見出しは日付の範囲だけにして、週名との二重表示をやめた。
  - **検証の仕方**: 「押せるか」ではなく、**見えている文字に「今週」が何回出るか**を
    数える。今週を見ているときだけ 1 回、それ以外は 0 回
    （操作名の「今週へ戻る」は除いて数える）。要素の状態ではなく、
    利用者が読む文字そのものを見ないと、この種の違和感は検出できない。

### D-047: 埋め込み地図は「タップして操作」まで指を奪わない／スポット種別を拡充（2026-08-08）

**① 地図がページのスクロールを奪う**

- **報告**: スポット編集で地図が大きすぎて下のボタンに気づかず、
  さらにスクロールしようとすると地図が動いてしまう。
- **原因**: Leaflet は既定で 1 本指のドラッグを地図の移動として取ってしまう。
  指が地図の上にあると、ページを縦に送れない。
- **決定**: 画面に**埋め込む**地図は、最初は操作を止めて
  **「タップして地図を操作」の覆い**を出す（Google マップの埋め込みと同じ考え方）。
  覆いがある間は指の動きがそのままページのスクロールになり、
  タップした時点で地図を動かせるようになる。
  - マップ画面（SCR-004）は地図そのものが主役なので、この覆いは付けない。
  - **ホイールでのズームは全画面で常に切る**。流し読み中に暴発して、
    見ていた場所を見失うのが一番困る。
  - 検証は「覆いがある間 `leaflet-grab` が付かない」で行う。
    Leaflet はドラッグを受け付けている間だけこの class を付けるので、
    付いていない = 指の動きをページに渡している、と直接確認できる。

**② 下のボタンに気づかない**

- 埋め込み地図の高さを **190px → 150px**（1 画面に「地図 + その下のボタン」が入る高さ）。
- 編集パネルの保存・キャンセルを **sticky** にして、常に手が届く位置に置く。
  地図を縮めるだけでは、項目が増えたときに同じ問題が再発する。

**③ スポット種別（12 種へ・015）**

- 既存の 5 種（サーフ・磯・港湾・管理釣り場・河川）は外洋と淡水に偏っていて、
  **汽水域がまるごと抜けていた**。浜名湖が主戦場である以上、致命的な欠落だった。
- 分ける基準は「**釣り方が変わるかどうか**」。地形が違っても狙い方が同じなら分けない。
  - 追加: ゴロタ場・テトラ帯・河口・干潟・汽水湖・水路 / 運河・湖沼 / 池
  - **堤防は独立させず「港湾・堤防」にまとめた**。足場も狙う魚も港湾と実質同じで、
    分けても選ぶときに迷うだけになる。
  - ゴロタ場はサーフと磯の中間で、扱うルアーもレンジも違うので独立させた。
  - テトラ帯は港湾の中にもサーフ沿いにもあり、足場と狙う魚が変わるので独立させた。
- 並びは **海 → 汽水 → 淡水**（魚種の並び D-028 と同じ考え方）。
- DB 側の CHECK 制約も広げる。画面のバグで知らない値が入らないようにする。

### D-048: マップ画面の地図は dvh で測り、凡例は使っている種別だけ出す（2026-08-08）

- **報告**: SPOT MAP の地図が高すぎて、下にある凡例・スポット一覧に気づけない。
- **原因は 2 つあった。**
  1. 高さが `calc(100vh - 210px)` だった。**スマホの `100vh` は URL バーを
     隠した状態の高さ**なので、URL バーが出ている実際の表示領域からはみ出す。
     引き算の 210px も、ヘッダーとナビしか見ていなかった。
  2. D-047 で種別を 12 に増やしたぶん**凡例が 3 行になり**、その下の一覧を
     さらに押し下げていた。種別を増やした副作用を見落としていた。
- **決定**:
  - `100dvh`（動的ビューポート）で測り、引く量を **330px** にする。
    「ヘッダー + 凡例 + 一覧の見出し + 1 件目 + ボトムナビ」が残る値。
    `100vh` の行を先に置いて、dvh 非対応ブラウザでも破綻しないようにする。
  - **凡例は登録済みのスポットに実際に出ている種別だけ**にする。
    12 種を常に並べるのは凡例として読み取りにくく、場所も食う。
    スポットを足すと種別が増えるので `renderAll()` から引き直す。
- **確認の仕方**: 「地図の高さ」ではなく**要素の位置**で測る。
  390×664 の画面で、凡例・一覧の見出し・1 件目の上端が
  すべてボトムナビより上に来ることを検証した（地図 334px = 画面の 50%）。
  高さだけ見ていると、周りの要素が増えたときに同じ問題を繰り返す。

### D-049: ヘッダーの形は「ナビ先か詳細画面か」で決める（2026-08-08）

- **報告**: 潮汐がボトムナビの行き先になったのに、上部だけ他の画面と違う。
- **原因**: SCR-003 はもともとホームの「詳細 →」から開く**詳細画面**として作った
  ため、戻るボタン付きの `page-head` を使っていた。D-040 でナビの行き先に
  格上げしたときに、ヘッダーを直し忘れていた。
- **決定**: ヘッダーの種類は画面の**役割**で決める。
  - **`app-header`** … ボトムナビから直接開く画面（ホーム / 潮汐 / マップ / 釣果 / レシピ）。
    タイトルを左、補足を右。**戻るボタンは置かない**（どこへ戻るのかが定まらない）。
  - **`page-head`** … 何かから掘り下げて開く画面（釣果詳細・スポット詳細・設定など）。

- 右側の補足（地点名）は `label`（「舞阪堤（舞阪 と同時刻）」）ではなく
  `name`（「舞阪堤」）にする。基準観測点と時差は TIDE CHART の見出しと
  SUMMARY 下に出ており、狭いヘッダーで繰り返す必要がない。
  長い名前でもタイトルを押し潰さないよう、補足側だけを省略表示にする。
- **確認の仕方**: 見た目を目で比べるのではなく、ナビ先 5 画面のヘッダーの
  **class・戻るボタンの有無・タイトルの左端・高さ・書体・文字サイズ**を
  取り出して突き合わせた（5 画面すべて左端 16px / 高さ 73px / Bebas Neue 26px）。

### D-050: 釣行スコアは「規則表」を正とし、当たった規則を画面で示す（2026-08-08）

- **要望**: 釣行スコアをタップしたら計算式が分かるようにしてほしい。
- **やらなかったこと**: ホバー用のツールチップ。主な利用環境が iPhone で、

  決まったか」を返す。画面はその配列をそのまま並べて i 番目を光らせるだけなので、
  規則を足す・直すと説明も自動で追従する。

  （全一致）。画面側は、円やセルに出ている星の数・ダイアログの星の数・

  状態を作らない。
- **その後**: この説明を出したことで「12 時を代表値にする根拠は？」という指摘に
  つながり、判定そのものを見直すことになった（D-051）。**説明を書けない仕様は

### D-051: 釣行スコアは朝マヅメ・夕マヅメで判定する（2026-08-08）

- **指摘**: 12 時（ホームは「現在時刻」）を代表値にしている根拠は何か。
  朝マヅメ・夕マヅメをそれぞれ代表値にすべきではないか。
- **これまでの根拠**: 実は**釣りの根拠は無かった**。12 時は
  「過去日・未来日でも同じ基準になる」という**比較の都合**だけで選んだもの
  （D-039）。ホームの現在時刻は「今の空模様」を出すついでにスコアも同じ値で
  出していただけで、夜に開くと真っ暗な時間の風でスコアが決まっていた。
- **決定**: **朝マヅメ・夕マヅメをそれぞれ判定し、良いほうをその日のスコアにする。**
  - マヅメの中心時刻は**日の出・日没そのもの**（Open-Meteo の daily から取得済み）。
  - 予報は 1 時間刻みなので、中心にいちばん近い時刻の 1 行を代表値にする
    （例: 日の出 05:04 → 5 時）。実際の竿出しは前後 1 時間ほどだが、
    その粒度の差はスコア 5 段階には効かない。
  - 潮回りは日単位なので、朝と夕で差が出るのは**天気と風だけ**。
  - 日の出・日没が取れない日（予報 16 日より先など）は 12 時に退避し、
    「12 時で見ている」とダイアログに明記する。
- **なぜ「良いほう」か**: スコアが答えるのは「今日は行く価値があるか」。
  朝が荒れていても夕が凪ぐ日は行く価値がある。ただし**どちらが良いかを隠さない**
  ため、ホームはタグに採用したマヅメの時刻を出し、潮汐画面はセルに
  「朝 3 / 夕 3」を添え、ダイアログでは 2 行を並べて採用側を光らせる。
- **確認の仕方**: 純粋関数として、代表時刻の選び方（05:02→5 時 / 18:44→19 時）・
  朝夕どちらを採るか・同点なら朝・日の出無しの退避・天気無しの null を検証。
  画面側は「円やセルの星」「ダイアログ上部の星」「採用マヅメの星」「光る規則の星」の
  **4 つが一致すること**を、日を切り替えた後も含めて確認した。
- **副産物**: 12 時が雷雨でもマヅメが凪いでいれば高得点になる。
  旧基準では 1 点だった日が 5 点になり得る（テストで差が出ることを確認済み）。
- **今後**: マヅメに**潮が動いているか**を加点要素にする案がある
  → **D-052 で採用**。

### D-052: マヅメに潮が動いているかで ±1 する（2026-08-08）

- **根拠**: 利用者の実釣経験。「**潮が流れ出すタイミングでよく食ってくる**」。
  D-018 の規則表は潮**回り**（大潮・中潮…）しか見ておらず、
  同じ大潮でも「マヅメが潮止まりの日」と「マヅメが動き出しの日」を区別できなかった。
- **決定**: マヅメの時刻の**潮の動き**で素点に ±1 する。
  | 判定 | 加減点 |
  | --- | --- |
  | 動き出し（潮が動きはじめて速くなっていく） | **＋1** |
  | よく流れている（ピークを過ぎて緩んでいく） | ±0 |
  | 潮止まり前後（ほとんど動いていない） | **−1** |
  最終スコアは 1〜5 に収める。「動き出し」を最上位に置いたのは上記の実釣経験そのまま。
- **速さは「その日いちばん速い流れとの比」で測る**（0.3 未満を潮止まりとする）。
  ここが設計の肝で、cm/h の絶対値で線を引くと**小潮の日は一日じゅう潮止まり判定**に
  なってしまう。潮回りはすでに素点に入っているので、それでは**二重に減点**することになる。
  比で測れば「小潮なりに動いている時間帯」を拾える
  （検証: 同じ時刻で大潮 34.5cm/h・小潮 5.0cm/h だが、どちらも「動き出し」と判定）。
- **加速しているかどうか**は 1 時間後の流速と比べて判定する。潮位は毎時値の
  線形補間なので、これ以上細かく測っても精度は上がらない（`tideAt()` と同じ考え方）。
- **荒天には加点しない**: 素点が「雷雨・強風」「雨・強風」の規則で決まった場合
  （規則表の 1〜2 番目）は潮を見ない。荒れている日を潮の動きで持ち上げないため。
  減点もしない（すでに最低点付近なので意味がない）。
- **どちらのマヅメを採るかは加減点込みの点で決める**。素点が同じでも、
  潮が動いているほうのマヅメが選ばれる。
- **画面**: マヅメの行に「下げ潮 動き出し ＋1」まで出し、
  採用したマヅメの**内訳（素点 → 潮の加減点 → 合計）**を 3 行で示す。
  加減点の規則表も並べ、当たった 1 行を光らせる（D-050 と同じ作り）。
- **確認の仕方**: 12 時間周期の理想的な潮位（正弦波）を作り、
  満潮・干潮ちょうど＝潮止まり、干潮 2 時間後＝動き出し、満潮 1 時間前＝流れている、
  を検証。加えて 上限 5・下限 1 のはみ出し防止、潮位なしで ±0、
  荒天ゲート、採用マヅメの決まり方、画面の「素点＋加減点＝合計＝円の数字」の
  一致まで通しで確認した。

### D-053: 日の出・日没はグラフ下の帯にアイコンで置き、潮汐画面は 1 画面 12 時間にする（2026-08-08）

- **要望**: 日の出・日没の時刻をグラフに載せてほしい。文字ではなくアイコンで。
  表示幅は 24 時間から 12 時間に狭めてよい。
- **アイコンを SVG の中に描かなかった理由**: 潮汐グラフは
  `preserveAspectRatio="none"` で横に引き伸ばしている（viewBox 幅より実寸が広い）。
  中にアイコンを置くと**丸が楕円に潰れる**。そこで
  **グラフの直下に HTML の帯を重ね、位置だけ `left: %` で合わせる**。
  形はそのまま保たれ、親の幅が 300% でも 1400% でも位置は狂わない。
  グラフ側には破線の縦線だけを引いて、帯のアイコンと視線をつなぐ。
- **凡例からは外した**: 「日の出 05:04 / 日没 18:45」をグラフ下の凡例に出していたが、
  グラフ上に置いた以上は重複。しかも凡例は**選択中の 1 日ぶん**しか出せず、
  複数日を 1 本でつないでいるこのグラフとは相性が悪かった。
- **1 画面 = 12 時間（潮汐画面のみ）**: `.tide-track` を 700% → 1400% に広げる。
  ホーム（SCR-001）は「本日の潮汐をひと目で」が役目なので 24 時間のままにした。
- **viewBox も同じ倍率で広げる**（`DAY_UNITS` 320 → 640）。ここを忘れると
  横の引き伸ばし率が 2 倍になり、**時刻ラベルが横に潰れて読めなくなる**。
  引き伸ばし率が 24 時間表示のときと変わらないことをテストで固定した（1.113 倍）。
- **スクロール計算はすべて「1 日ぶんの実寸」に集約**した（`dayWidth()`）。
  以前は `clientWidth` ＝ 1 日ぶんという前提が
  `scrollToDate` / `scrollToNow` / `centeredDate` / `loadVisibleDays` に散らばっていた。
- **確認の仕方**: 位置は「アイコンの中心が**夜の帯の境目**と一致するか」で見た
  （日の出＝帯の右端、日没＝帯の左端。実寸で誤差 0px）。
  どの日の天気が届いているかは通信状況で変わるので、
  「3 日ぶん出ているか」ではなく**印・夜の帯・縦線の数が揃うか**を不変条件にした。
  アイコンが正円のまま（12×12）であることも実寸で確認している。

### D-055: 週間カレンダーに釣行スコアを出す。天気は週まとめで 1 回だけ取る（2026-08-08）

- **狙い**: カレンダーに潮回りと天気しか無く、「今週いつ行くか」が決められなかった。

- **予報外の週を叩き続けない**: 予報の届かない週は結果が空のまま返るので、

  週ごとに覚える（進行中の Promise を持たせて二重取得も防ぐ）。
- **確認の仕方**: カレンダーの星と、その日を開いたときのサマリの星が一致すること
  （2 日ぶんで確認）。リクエスト数は実際の通信を数えて固定した。

### D-056: 日の出・日没は API から取らず計算する（2026-08-08）

- **きっかけ**: 釣果詳細に「その 1 匹はマヅメだったか」を出したかったが、

### D-059: 招待リンクは 1 本 1 人のまま、まとめて作れるようにする（2026-08-08）

- **報告**: 招待リンクで 1 人が登録したあと、同じリンクから別の人が登録しようとしたら
  「既に登録済み」になった。
- **調べたこと**: 招待は**使い切り**（`used_by` / `used_at`）で、DB を見ると
  リンクは 1 本しか作られておらず、こだまさんが使い切っていた。つまり
  **仕様どおりの動作**。2 人目のアカウントは作られていない（データへの影響なし）。
- **本当の問題は画面が黙っていたこと**: 「招待リンクを作る」ボタンと
  「本人にだけ送ってください」しか書いておらず、**1 回使うと閉じる**ことを
  伝えていなかった。3 人招待するには 3 本必要、という前提が隠れていた。
- **決定（利用者判断）**: 使い切り仕様は**変えない**。1 本で複数人が登録できるように
  すると、リンクが転送されたときに知らない人でも上限まで入れてしまう。
  代わりに **人数ぶんまとめて作れる**ようにし、画面に明記する。
  - 「何人ぶん作るか」を選べる（選べる上限＝グループの残り席）
  - メモを付けて 2 本以上作ると「たろう 1」「たろう 2」と番号が付いて区別できる
  - **未使用の招待も席として数える**。3 本作ってから「あと 5 人」と出ると二重に招待してしまう
  - **使用済みの招待も一覧に残す**（いつ使われたか）。3 本送って誰が使ったか
    分からないと催促のしようがない。ただしリンクのコピーと取り消しはできなくする
- **ついでに直した詰み**: 招待の消化はアカウント作成より**前**に行うが、
  作成の**後**に失敗した場合（プロフィール更新や `redeem_invite` の失敗）、
  招待は解放されるのに**アカウントだけ残っていた**。この状態でやり直すと
  「このメールアドレスは既に登録されています」で弾かれ、
  **グループに入れないまま永久に詰む**。失敗時は作りかけのアカウントも消すようにした。
- **確認の仕方**: 巻き戻しは「わざと途中で失敗する版」を
  **別名の関数として一時的にデプロイ**して検証した（本番の `invite` には触らない）。
  失敗 → 同じメールアドレスでやり直せることを確認し、検証用の関数は削除済み。
  あわせて 3 本まとめて作る／2 人目が同じリンクで弾かれる／別のリンクなら通る／
  登録済みメールで失敗しても招待は無駄にならない、を実際の通信で確認した。

### D-060: `groups.owner_id` に外部キーが無かった（2026-08-08）

- **見つけ方**: D-059 の検証でテスト用のオーナーを消したら、**グループだけ残った**。
- **原因**: `public.groups` には外部キーが**1 本も無かった**（PRIMARY KEY だけ）。
  子テーブル（`group_members` / `group_invites`）は最初から
  `ON DELETE CASCADE` だったのに、親の `owner_id` が素の UUID だった。
- **残ると何が困るか**: `is_group_owner()` は `owner_id = auth.uid()` で判定するので、
  居ないユーザーが owner のグループは**誰もオーナーになれない**。招待も作れず、
  名前も変えられず、メンバーは抜けることしかできない。
  D-059 で直した詰みと同じ「そこから出られない状態」。
- **決定**: `owner_id` → `profiles(id)` の FK を `ON DELETE CASCADE` で張る
  （migration 017）。参照先を `profiles` にしたのは既存の 2 つと揃えるため。
  `profiles` 自体が `auth.users` を CASCADE で参照しているので、退会すれば連鎖して消える。
  張る前に、参照先の居ないグループ（＝機能しないグループ）を削除している。

  - 保存直後の遷移先が `records.html` ではなく `record.html?id=…` だった。

  - 同じ端末から前後に 2 枚（371KB / 328KB の WebP）は成功している。
  - → **通信の前、端末の中で失敗している**。特定の 1 枚だけが駄目だった。
- **原因は特定しきれない**。クライアント側の失敗はどこにも記録が残っておらず、
  画面も「写真の保存に失敗しました」としか出していなかった。**これが一番の問題**なので、
  考えられる原因を潰したうえで、**次は理由が分かるように**した。
- **直した 1: デコードを 1 回に減らす。** 表示用とサムネイルで
  `shrinkImage(file)` を**同じ写真に 2 回、しかも並行に**呼んでいた。
  高画素の写真では原寸ビットマップ（例: 8000×6000 なら約 190MB）が
  同時に 2 つ載る。1 回デコードして 2 枚描くように変え、メモリの山を半分にした。
- **直した 2: デコードを段階的に試す。**
  ①そのまま → ②`resizeWidth` を付けて縮小しながら（原寸ビットマップを作らずに済む）
  → ③`<img>` 経由。巨大な写真は②で救える。
- **直した 3: 失敗の理由を画面に出す。** 例外の message を握りつぶしていたので、
  `sessionStorage` 経由で釣果詳細まで運ぶようにした。
  デコード不能なら **MIME 型まで書き**、HEIC のときの対処（カメラ設定を JPEG にする等）も添える。
- **確認の仕方**: `createImageBitmap` を差し替えて**呼ばれた回数**を数えた
  （写真 1 枚のアップロードで 1 回。以前は 2 回）。1 段目をわざと失敗させて
  2 段目に `resizeWidth: 1600` が渡ることも確認。
  デコード不能な HEIC で「形式付きのエラー文が釣果詳細に出る」ところまで通した。
- **残っている宿題**: クライアント側の失敗は今も**サーバに残らない**。
  同じことが起きたら、また本人の画面を見るしかない。
  件数が増えるようなら失敗を 1 行だけ記録する仕組みを考える。

### D-062: 潮回りは「実際の朔からの旧暦日」で決める（D-002 の計算を破棄）（2026-08-09）

- **報告**: 「潮汐がずれている。今日は中潮のはず」。
  2026-08-09 は**長潮**と出ていた。正しくは**中潮**。
- **原因は 2 つ重なっていた**。どちらも D-002 からの持ち越し。
  1. **平均の朔望月を積み上げていた**。2000-01-06 の朔から 29.530588853 日ずつ
     数えていたが、実際の朔は平均から最大 ±0.6 日ずれる。
  2. **月齢と旧暦日を同じものとして扱っていた**。潮名は旧暦日で決まるが、
     旧暦日は「**朔の日を 1 日目と数える日付**」であって経過時間ではない。
     2026 年 7 月の朔は **7/14 18:43 JST**。その日の正午の月齢はまだ 29 日台なのに、
     旧暦ではもう 1 日。ここで丸ごと 1 日ずれ、①と合わせて 2 日ずれていた。
- **決定**: Meeus『Astronomical Algorithms』49 章で**実際の朔の時刻**を求め、
  旧暦日（朔の日が 1 日目）から潮名を引く。月齢も実際の朔からの経過日数にする。
- **気象庁の潮位表で裏を取った**（舞阪・2026 年の 365 日）。
  潮名は本来「日較差（その日の最高潮位 − 最低潮位）」の大小に対応する。
  | | 大潮 | 中潮 | 小潮 | 長潮 | 若潮 |
  | --- | --- | --- | --- | --- | --- |
  | 直す前 | 114.7 | 96.8 | 66.9 | **76.4** | **87.4** |
  | 直した後 | 113.6 | 97.6 | 71.6 | **66.6** | **75.3** |
  **長潮は「日較差がいちばん小さい日」**を指すのに、直す前は小潮より大きかった。
  直した後は 長潮 < 小潮 < 若潮 < 中潮 < 大潮 と、意味どおりの順序になる。
  8 月の実データで見ると、直す前は日較差が最小の 8/7 を「小潮」、
  すでに増え始めた 8/9 を「長潮」、105cm まで育った 8/10 を「若潮」と呼んでいた。
- **3 か所を揃えた**: フロント（`app.js`）・潮汐 API（`functions/tide/parser.ts`）・
  DB（`tide_type()` / `moon_age()`）。**画面に出るのは潮汐 API の値**なので、
  ここを直さないと表示は変わらない。
- **SQL には計算式を書かない**。Meeus を PL/pgSQL で書くと誰も読めなくなるので、
  同じ計算で作った**朔の時刻の表**（`moon_new_moons`・1990〜2080 の 1125 行）を持ち、
  SQL は引くだけにした。範囲外は NULL（黙って間違えるよりよい）。
- **保存済みの釣果も引き直した**（migration 018 / 019）。潮回りも月齢も
  釣行日から決まる派生値で、入力値ではない。6 件のうち 4 件の潮回りが変わった。
- **確認の仕方**: フロントと DB を **2024〜2030 年の 2,557 日**で突き合わせ、
  旧暦日・月齢・潮名すべて不一致 0。朔の日が必ず旧暦 1 日・大潮になること、
  旧暦日が 1〜30 に収まることも確認。画面・潮汐 API の実際の応答まで通した。

### D-070: 地名検索は住所と施設の 2 本立てにする（2026-08-09）

- **報告**: 「アルクスポンド焼津」（管理釣り場）も「庄内湖」も検索できなかった。
  スポット登録のとき、地点名の入力欄が地図に埋まって表示できなかった。

#### 1. 検索できなかった理由

- D-069 で使った国土地理院の地名検索は、**住所（と大きな地名）の索引**だった。
  管理釣り場のような施設名も、湖の中の小さな水域名も、そもそも入っていない。
  「外部サービスが落ちるかもしれない」ことは想定していたが、
  **索引の中身が要る範囲と違う**ことを確かめていなかった。
  釣り場は住所で呼ばれない場所が多い、という当たり前の点を外していた。

- **OpenStreetMap（Nominatim）を足して、両方に投げて混ぜる**ことにした。
  施設・地物の索引なので、管理釣り場・湖・漁港・ダムはこちらが拾う。
  地図タイルは国土地理院のままで、**検索だけ借りる**。
  - 片方が落ちても、もう片方の結果を返す。
    両方だめなときだけ「つながらなかった」にする。
  - 同じ場所が両方から返ることがあるので、名前が同じで 200m 以内ならまとめる。
  - **探した言葉に近い名前を先に出す**。これが無いと、
    「アルクスポンド焼津」で住所側が拾った「焼津市」が先頭に来てしまう。
  - 候補には**住所も添える**（「アルクスポンド焼津 / 焼津市, 静岡県」）。
    同じ名前の場所が並んだときに、これが無いと選べない。
  - OpenStreetMap のデータは表示するときに出典が要るので、候補の下に出す。

- **貼り付けの案内を、困る前から出すことにした**。D-069 では
  「見つからなかったとき」にだけ出していたが、**管理釣り場や小さな池は
  どの地名データにも載っていないことがある**以上、これは例外処理ではなく
  正規の入口の 1 つ。検索欄の下に常時 1 行置く。

- **それでも足りないなら**: Google マップの POI 収録には、無料の範囲では
  どの経路でも届かない（API キーと課金が要る）。URL を貼る道が本命の逃げ道であり、
  だから常時見せる、という整理にした。

#### 2. 入力欄が埋まっていた理由

- `.map-tools`（航空写真・夜間・現在地・追加）は地図の右上から**下へ伸びる**が、
  地図の高さでは切られない。一方で登録シートは `z-index: 22`、
  ツールは `500`。**シートの上にボタンが乗っていた**。
- 実測すると、幅 390 / 高さ 640 の画面で「スポット名」の欄が `y 253〜295`、
  「やめる」ボタンが `y 244〜275`。**名前を入れようと右半分を触ると、
  登録が取り消されていた**。見えないだけでなく、操作を奪っていた。
- シートを `z-index: 600` に上げた。
  併せてシートの上限を `62dvh → 52dvh` に下げている。
  D-069 で案内文を 1 行足したぶん地図が下がり、
  見える帯が 50px しか残らなくなっていたため。

- **確認の仕方**: シートの中の入力欄・ボタン・チップを**総当たりで**、
  それぞれ 3 点について `elementFromPoint` で「上に何が乗っているか」を実測した
  （シート自身がスクロールするので、見えている箱の中だけを対象にする）。
  修正前は「やめる」ボタンが名前欄を覆い、修正後は 0 件。
  検索側は、応答を差し替えて 36 項目
  （管理釣り場が出ること・順位・片方が落ちたときの動き・出典表記など）。
  提供元ごとの JSON の読み取りは `frontend/tests/search_place.test.mjs` で
  15 通り、本物の応答の形に合わせて固定した。

- **未確認**: サンドボックスから両サービスへ出られないため、
  **本物の応答と CORS 許可は今回も通せていない**。
  実機で「アルクスポンド焼津」が出るかどうかは、OpenStreetMap にその施設が
  登録されているか次第。出なければ URL 貼り付けで登録できる。

### D-072: 短縮 URL はサーバー側で開く。座標が無ければ住所から求める（2026-08-09）

- **要望**: `https://maps.app.goo.gl/e2JECSwyPL3opXuz5?g_st=ac` の形式で検索できないか。

- **ブラウザからは解けない**。短縮 URL に座標は入っておらず、
  リダイレクトを追った先の長い URL で初めて分かる。ところが goo.gl は
  CORS を許していないので、`fetch` の結果は不透明になり、
  飛んだ先の URL（`response.url`）が読めない。`no-cors` でも同じ。
  **サーバー側で 1 回踏むしかない**ので、Edge Function を 1 本足した
  （`resolve-map-link`）。

- **やってみて分かったこと**（報告された URL をそのまま流して確かめた）
  - 飛んだ先は
    `.../place/〒421-0212 静岡県焼津市利右衛門１１５ アルクスポンド 焼津/data=!4m2!3m1!1s0x…:0x…`。
    **これは「検索できなかった」あの管理釣り場そのものだった。**
  - **座標が入っていない**。`data=` にあるのは場所の ID だけ。
    本文（805KB）にも無い。座標は地図の JavaScript が後から入れるため、
    HTML を取っただけでは出てこない。UA をデスクトップにしても、
    CID から開き直しても同じだった（どれも実際に試した）。
  - 一方で**住所は URL に入っている**。国土地理院で
    `静岡県焼津市利右衛門` → `[138.295471, 34.788067]` と引ける。

- **決めたこと**: 座標があればそれを使い、無ければ**住所から求めて
  「おおよその位置」だと伝える**。大字までしか当たらないので、
  施設そのものの位置ではない。黙って置くと「ここでいい」と思ったまま
  登録されてしまうので、**住所を添えて、直すように促す**。
  施設名（「アルクスポンド 焼津」）はスポット名に入れる。

- **踏み台にしないための作り**
  - **行き先は固定の候補に完全一致するホストだけ**。
    `endsWith(".goo.gl")` のような書き方はしない（`evil-goo.gl` が通る）。
  - `redirect: "follow"` に任せず**1 つずつ手で追う**。任せると最初の 1 回しか
    確認できず、途中で外へ飛ばされても気づけない。上限は 5 回。
  - 本文はそのまま返さない。座標と名前だけを返す。
  - `example.com` / `169.254.169.254`（メタデータ）/ `evil-goo.gl` が
    弾かれることを実際に叩いて確かめた。

- **`verify_jwt = true` だけでは足りなかった**。
  **publishable（anon）キーだけで通ってしまう**ことを叩いて確かめた
  （apikey のみ → 200）。このキーは画面に埋め込んで配る公開キーで、
  リポジトリも公開しているので誰でも拾える。外へ取りに行く関数を
  開けたままにすると、短縮 URL の展開屋として実行回数を使い潰される。
  関数の中でも**利用者のトークンかどうかを Auth に聞く**ようにした
  （公開キーのみ → 401、ログイン済み → 200 を確認）。

- **ついでに確かめられたこと**: D-069・D-070 で「未確認」と書いていた
  **地名検索の CORS 許可**。Edge Function から `Origin` を付けて叩いたところ、
  国土地理院・OpenStreetMap ともに `Access-Control-Allow-Origin: *` を返した。
  ブラウザから使える。報告（庄内湖などは検索できた）とも一致する。
  併せて**「アルクスポンド焼津」「アルクスポンド」はどちらの索引にも無い**ことも
  確認した（D-070 の見立てのとおり、データに無いだけ）。

- **確認の仕方**: 純粋な読み取り（座標・住所と名前の切り分け）は
  `supabase/functions/resolve-map-link/parse.test.mjs` に 7 件。
  実物の URL をそのまま入れてある。`index.ts` は読み込むだけで
  `Deno.serve` が動いてしまうので、読み取り部分を `parse.ts` に分けた。
  画面側は**本番の Edge Function をそのまま叩いて**、
  ピンが立ち・名前が入り・おおよそであることが伝わるところまで通した。

### D-025: フロントは素の CSS + vendoring した supabase-js（ビルド工程なし）（2026-07-18）

- **決定**: 当面 Tailwind のビルド工程を導入せず、ワイヤーフレーム v7.2 と同じ
  CSS 変数を持つ `frontend/assets/theme.css` を使う。supabase-js は npm から

  素の CSS で書かれているため見た目の再現性も高い。
- **見直し条件**: Phase 2 で画面数が増えて CSS が肥大化したら Tailwind の
  ビルド工程（Pages ワークフローに 1 ステップ追加）を検討する。
